# jinja-build Server

## 设计特性

### 模板根目录

服务端固定使用一个模板根目录。请求只需要选择这个根目录里的相对模板路径，适合把可用模板范围收在部署侧。

模板路径既可以指向目录，也可以指向单个模板文件。目录模式会沿用本地渲染的相对层级输出规则。

### 请求渲染

每次请求上传本次输入配置。服务端按请求内容完成一次渲染，调用方直接拿到生成后的文件。

单个模板会返回一个文件。模板目录会返回一个压缩包，里面保留模板目录下的相对层级。

### 运行日志

服务端会把请求和渲染结果写入日志目录。每次启动都会按日期和时间创建本次日志，路径形如 `20260502/004301.log`。

错误日志会保留异常堆栈。这样模板内容、数据结构或配置导致的问题可以回头排查，不需要盯着终端输出。

### 访问边界

服务端默认面向外部访问。部署机器、防火墙或上层网关决定谁能连进来。

调用方被视为可信用户。服务端只检查上传配置文件的大小是否正常，明显异常时直接返回错误。

### 路径提示

当请求里的模板路径找不到时，响应会带上一个相近路径。调用方可以直接用这个提示修正拼写或目录层级。

可选路径来自服务端允许使用的模板范围。这样错误提示和可用模板保持同一边界。

### 数据建模

模板旁边放一份数据结构定义，输入会先转成稳定的数据对象。模板看到的是整理后的数据，不需要自己处理原始配置里的细节。

数据对象上的公开方法也会放进模板可用范围。适合把常用计算收在数据附近，避免模板里写太多判断。

### 空白输出

模板渲染后如果只剩空白内容，就不会写出文件。条件模板可以靠这个规则自然跳过，不需要额外维护文件清单。

这个规则按渲染结果判断。全是空格或换行也会被当作空内容。

## 配置

### `port`

| 参数 | 说明 | 默认 |
| --- | --- | --- |
| `-p`, `--port` | 服务端对外使用的端口号。 | 无 |

### `template`

| 参数 | 说明 | 默认 |
| --- | --- | --- |
| `-t`, `--template` | 服务端允许使用的模板根目录。 | 无 |

### `log`

| 参数 | 说明 | 默认 |
| --- | --- | --- |
| `-l`, `--log` | 服务端写入的日志目录。 | 无 |

### `request`

| 键 | 说明 | 默认 |
| --- | --- | --- |
| `template` | 相对服务端模板根目录的模板路径。 | 无 |
| `input` | 上传的输入配置文件。 | 空配置 |
| `models_filename` | 模板目录中的数据结构文件名。 | `models.py` |

## 调用

请求地址是 `POST /render`。请求体使用 `multipart/form-data`，普通字段放模板参数，文件字段 `input` 放本次输入配置。

用 `curl` 请求时可以直接让客户端按响应头保存文件：

```bash
curl -OJ -X POST "http://127.0.0.1:8000/render" \
  -F "template=site" \
  -F "input=@input.json" \
  -F "models_filename=models.py"
```

如果模板路径指向单个模板文件，响应就是渲染后的文件。如果模板路径指向目录，响应是一个 zip 包。

输出文件由调用方保存。`curl -OJ` 会读取响应头里的文件名，直接保存到当前目录。

需要自己指定保存位置时，用 `-o`：

```bash
curl -L -X POST "http://127.0.0.1:8000/render" \
  -F "template=site" \
  -F "input=@input.json" \
  -o output.zip
```

不需要输入配置时，可以省略 `input`：

```bash
curl -OJ -X POST "http://127.0.0.1:8000/render" \
  -F "template=site"
```
