# jinja-build Server

jinja-build Server 把模板渲染能力放到 HTTP 服务里，调用方上传输入配置后直接拿到生成文件。

- 模板范围由服务端固定，调用方只选择相对模板路径。
- 单个模板返回文件，模板目录返回 zip 包。
- 每次请求独立渲染，适合由其他系统按需调用。
- 找不到模板时会给出相近路径，方便修正请求。
- 请求和异常会写入日志，便于回头排查。

## 设计特性

### 模板根目录

服务端先圈定一个模板根目录，调用方只在这个范围里选择模板。

这样可用模板由部署侧管理，请求里不用传真实文件位置。模板路径既可以指向目录，也可以指向单个模板文件。

### 请求渲染

一次请求就是一次完整渲染。

```text
模板文件 + 输入配置 -> 文件响应
模板目录 + 输入配置 -> zip 响应
```

目录模式会保留模板目录下的相对层级，调用方拿到结果后自行保存。

### 运行日志

请求、渲染结果和异常都会进入本次启动的日志。

日志按日期和时间分层写入，例如 `2026-05-02/00-43-01.log`。模板内容、数据结构或输入配置导致的问题，可以从异常堆栈回头排查。

### 访问边界

Server 只负责渲染请求，不替部署环境做访问控制。

- 谁能连进来，由部署机器、防火墙或上层网关决定。
- 调用方被视为可信用户。
- 上传配置会做大小检查，明显异常时直接返回错误。

### 路径提示

模板路径写错时，响应会带一个相近路径。

这个提示来自服务端允许使用的模板范围，既能帮助修正拼写，也不会越过部署侧圈定的边界。

### 数据建模

模板拿到的是整理后的数据，不是原始配置。

```text
上传配置 -> 数据对象 -> 模板
```

常用计算可以收在数据附近，让模板少处理字段细节和判断逻辑。

### 空白输出

让模板自己表达“要不要生成”。

渲染后只剩空白内容时，不会写出对应文件。这个判断看最终结果，全是空格或换行也算空内容。

## 配置

### `port`

| 参数 | 说明 | 默认 |
| --- | --- | --- |
| `-p`, `--port` | 服务端对外使用的端口号。 | 无 |

### `template`

| 参数 | 说明 | 默认 |
| --- | --- | --- |
| `-t`, `--template` | 服务端允许使用的模板根目录。 | 无 |

### `log`

| 参数 | 说明 | 默认 |
| --- | --- | --- |
| `-l`, `--log` | 服务端写入的日志目录。 | 无 |

### `request`

| 键 | 说明 | 默认 |
| --- | --- | --- |
| `template` | 相对服务端模板根目录的模板路径。 | 无 |
| `input` | 上传的输入配置文件。 | 空配置 |
| `models_filename` | 模板目录中的数据结构文件名。 | `models.py` |

## 调用

请求地址是 `POST /render`。请求体使用 `multipart/form-data`，普通字段放模板参数，文件字段 `input` 放本次输入配置。

用 `curl` 请求时可以直接让客户端按响应头保存文件：

```bash
curl -OJ -X POST "http://127.0.0.1:8000/render" \
  -F "template=site" \
  -F "input=@input.json" \
  -F "models_filename=models.py"
```

如果模板路径指向单个模板文件，响应就是渲染后的文件。如果模板路径指向目录，响应是一个 zip 包。

输出文件由调用方保存。`curl -OJ` 会读取响应头里的文件名，直接保存到当前目录。

需要自己指定保存位置时，用 `-o`：

```bash
curl -L -X POST "http://127.0.0.1:8000/render" \
  -F "template=site" \
  -F "input=@input.json" \
  -o output.zip
```

不需要输入配置时，可以省略 `input`：

```bash
curl -OJ -X POST "http://127.0.0.1:8000/render" \
  -F "template=site"
```
